## 1. Ranked shortlist — the 7 products that matter for AEGIS

Ranked by *transferability to an operator console for regulated work*, not by fame.

### 1. Temporal UI — `github.com/temporalio/ui`
**Why us, specifically:** it is the closest structural analogue that exists. A Temporal workflow
execution *is* an AEGIS run: a long-lived, multi-stage, replayable process with a durable event
history where every state transition is a recorded, attributable fact. Temporal's UI has already
solved (a) how to show a pipeline that is mid-flight without lying about it, (b) how to colour-code
*kinds of event* without burning your status palette, and (c) how to make an append-only history
navigable. If you steal one information architecture, steal this one.

### 2. Vercel / Geist — `vercel.com/geist`
**Why us:** you are already on Geist Sans/Mono, so the type is a free match. More importantly Geist
is the most complete public demonstration of *separation by 1px ring rather than by shadow* — which
is exactly the discipline a dense, paper-coloured compliance console needs. Its whole elevation
system is `box-shadow: 0 0 0 1px <alpha black>` plus progressively softer offset layers. It is a
system you can copy wholesale into Tailwind v4 tokens in an afternoon.

### 3. Linear
**Why us:** the canonical reference for "restrained but alive". One accent hue, four background
levels, and — the part nobody copies — a *separate token family for hairlines vs. control borders*.
Its motion model (instant in, gentle out; 100 ms default) is the single cheapest change you can make
that will read as expensive to a judge clicking through. Also: 232 px sidebar, and a type scale whose
letter-spacing tightens as size grows.

### 4. Sentry — `github.com/getsentry/sentry`
**Why us:** Sentry's entire product is *showing failure honestly*, which is your explicit requirement.
It is also the best public example of design tokens generated by a design-engineering pipeline
(`// AUTOGENERATED BY @DESIGN-ENGINEERING`), with genuinely considered motion tokens — separate
`enter` and `exit` easing curves, and a 120/160/240 ms duration ladder. And a detail nobody else
ships: mono regular weight is **425**, not 400.

### 5. Grafana — `github.com/grafana/grafana` + `play.grafana.org`
**Why us:** it is the densest operator console that is fully open and fully measurable, and it is the
one most of your judges will have seen in an industrial/plant context. Its 14 px base, 22 px line
height, 36 px row and all-even-numbers rule are battle-tested for wall-mounted, long-session reading.
It also demonstrates the *opacity-over-solid* colour model that keeps a dark theme coherent.

### 6. Stripe Dashboard
**Why us:** the trust-through-restraint benchmark, and the most relevant *tone*. Regulated money,
audit trails, irreversible actions. Two specifics are worth everything: their 2025 move to a
**card-less** dashboard (depth via background tint, never elevation), and their refusal to use pure
black ink — body copy is `#3c4257`, a desaturated navy. Your `#0a0a0a` on `#f7f7f5` is currently
harsher than Stripe's.

### 7. Supabase Studio
**Why us:** the most technically interesting colour system in the list. Supabase derives *every*
border from the foreground colour in OKLCH, with a user-facing contrast knob. For a warm-paper
palette this is the difference between hairlines that look grey and dirty, and hairlines that look
like they belong to the paper. This is a direct, high-leverage fix for AEGIS.

**Honourable mentions, not broken out:** Raycast (command-palette craft), Tailscale (light-weight
headline restraint in infra), Warp/Arc (chrome minimisation). All [REPORTED] only — see §4 and §5.

## 2. Per-product breakdown

### 2.1 Temporal UI

Source: `github.com/temporalio/ui` — `src/app.css`, `src/lib/theme/plugin.ts`,
`src/lib/theme/io/themes/theme-light.ts`, `src/lib/theme/io/themes/primitives.ts`.

#### Layout skeleton
**[SOURCE]** A single horizontal top nav at `--top-nav-height: 3rem` (48 px), with a mobile bottom
nav at `--bottom-nav-height: 4rem` (64 px) that is zeroed out at the `768px` breakpoint. There is
no persistent left sidebar in the shell — navigation is namespace-scoped and lives in the top bar,
because the primary object (a workflow execution) has a *deep* detail view rather than a wide one.

The shell computes scroll insets rather than using fixed padding:

```css
--scroll-inset-top: calc(var(--top-nav-height) + var(--banner-height));
--scroll-inset-bottom: 0px;      /* desktop */
```

**Why it suits the data, and us:** an execution list → execution detail → event history is a
*drill-down*, not a dashboard. Detail opens as a **route**, not a drawer, because the detail is
deep, bookmarkable and citable — you need to be able to send someone a URL that lands on event #47.
**For AEGIS this is the decision:** a run detail must be a route. An auditor has to be able to paste
a link into a report.

#### Density and rhythm
**[SOURCE]** Base body text is Tailwind `sm` = **14 px**; `body-small` is `xs` = **12 px**. The
heading ramp is `h1: 3xl → h6: sm`, and — notably — **every heading is `fontWeight.medium` (500)**.
There is no bold heading anywhere in the base layer. Separation is done with `border` tokens derived
from alpha scales, not shadows.

#### Colour discipline
This is the part to steal. **[SOURCE]** Temporal splits colour into five *semantic layers* rather
than a palette:

```
color.content.*      – text and icons
color.surface.*      – fills
color.border.*       – hairlines
color.interactive.*  – buttons, with rest / hover / press triples
color.action.*       – domain-meaningful colour (see below)
```

Each status gets a coherent **triplet from one 12-step Radix-style scale**:

| Status | content (text) | surface (fill) | border |
|---|---|---|---|
| success | `green[12]` | `green[4]` | `green` α60 |
| warning | `amber[12]` | `amber[2]` | `amber` α60 |
| danger  | `red[12]`   | `red[4]`   | `red` α60 |
| information | `blue[12]` | `blue[4]` | `blue` α60 |

Borders are literally `color-mix(in srgb, <hex> 60%, transparent)` — alpha, so the paper shows
through. There is also a separate `content.static.*` ramp at **step 11**, used when a chip sits on a
*coloured* surface rather than on the page. That is the detail that stops status pills from going
muddy.

And then the move that actually matters for AEGIS: **`color.action.workflow.*` colour-codes event
kinds on a completely separate hue budget from status.**

```
workflow  zaffre[9]        #0014a8
activity  dark-magenta[9]
signal    persimmon[9]
timer     pink[9]
nexus     peacock-blue[9]
query     slate-blue[9]
```

Six hues for *taxonomy*, four for *status*. They never collide, because taxonomy colour only ever
appears as a 2–3 px rail or a small glyph, never as a fill.

#### Typography
**[SOURCE]** Tailwind default sans; mono is used for exactly one named style, `.body-small-mono`
(12 px, regular weight) — reserved for IDs, run IDs, task queue names. Mono is a *semantic* choice,
not a decorative one.

#### The move that makes it feel expensive
The `content.static` ramp. Most teams have one "success green" and it either fails contrast on white
or looks radioactive on a green chip. Temporal ships two greens for text — step 12 for text on
paper, step 11 for text on a green fill — and the result is that every badge in the product has the
same optical weight. It costs you four extra tokens and it is the difference between a competent
badge set and a designed one.

Second: `opacity.disabled: '0.32'` as a single global token, applied by opacity rather than by a
grey colour. Disabled things keep their hue and just recede. Nothing turns to mud.

#### Empty, loading, error
**[INFERENCE from the token structure — I read the tokens, not every screen]** Temporal has
first-class `surface.warning` / `surface.danger` / `border.danger` tokens *and* a distinct
`content.error` built on a `persimmon` scale separate from `content.danger`'s red. Two different
reds: one for *destructive user action* (danger), one for *the system failed* (error). That
distinction is directly load-bearing for AEGIS, where "reject this task" and "verification failed"
must not be the same colour.

### 2.2 Vercel / Geist

Source: **[MEASURED]** live computed `:root` on `vercel.com/geist/colors`, 326 custom properties.

#### Layout skeleton
**[MEASURED]** `--ds-page-width: 1400px`; `--ds-page-width-with-margin: calc(1400px + calc(2 * 24px))`
— so a 24 px page gutter, always. Overlay layering is an explicit z-scale:

```
--ds-z-drawer: 200;  --ds-z-modal: 300;  --ds-z-menu: 2001;
--ds-z-toast: 5000;  --ds-z-tooltip: 99999;
```

Note the ordering: **menus sit above modals**. That is deliberate — a select inside a modal must not
be clipped. Steal the whole ladder; it is free and it prevents an entire class of bug.

#### Density and rhythm
**[MEASURED]** Three control heights, and only three:

```
--ds-size-small: 32px;  --ds-size-medium: 36px;  --ds-size-large: 40px;
```

Form typography is locked to those:

```
--geist-form-font: .875rem;        /* 14px */
--geist-form-line-height: 1.25rem; /* 20px */
--geist-form-height: 36px;
--geist-form-large-font: 1rem; --geist-form-large-line-height: 1.5rem; --geist-form-large-height: 40px;
--geist-form-small-font: .875rem; --geist-form-small-line-height: .875rem; --geist-form-small-height: 32px;
```

Menu/list rows have their own micro-system:

```
--ds-popover-padding: 6px;
--ds-popover-row-height: 36px;
--ds-popover-row-padding: 0 8px;
--ds-popover-row-radius: 6px;
```

A 6 px popover pad with 6 px row radius inside an 8 px container radius is the classic concentric-
radius trick: inner radius = outer radius − padding. It reads as machined.

Spacing is a strict 4 px scale: `4, 8, 12, 16, 24, 32, 40, 64, 96, 128, 192, 256` **[MEASURED]**.
Default radius `--geist-radius: 6px`.

#### Colour discipline
**[MEASURED]** Ten-step scales in `hsla()` for gray, blue, red, amber, green, teal, purple, pink —
*but* the working neutral is a **separate alpha scale**:

```
--ds-gray-alpha-100: #0000000d   (5%)
--ds-gray-alpha-200: #00000014   (8%)
--ds-gray-alpha-300: #0000001a   (10%)
--ds-gray-alpha-500: #00000036   (21%)
--ds-gray-alpha-600: #00000057   (34%)
--ds-gray-alpha-1000: #000000e8  (91%)
```

Solid grays for fills, alpha grays for *anything that overlays something else*. This is why Vercel's
UI never gets that "grey box on grey box" cast.

Backgrounds are only two steps: `--ds-background-100: hsla(0,0%,100%,1)` and
`--ds-background-200: hsla(0,0%,98%,1)`. Depth is done with rings, not with more greys.

The overlay backdrop is the detail to note: **[MEASURED]**

```
--ds-overlay-backdrop-color: hsla(0, 0%, 95%, 1);   /* light grey, NOT black */
--ds-overlay-backdrop-opacity: .8;
```

They dim a light UI with a *light* scrim. Black scrims make a paper-coloured product look cheap and
make the modal look like it is floating in a void. On `#f7f7f5` paper, AEGIS should scrim with a warm
near-white at ~0.8, not `rgba(0,0,0,.5)`.

#### Typography
**[MEASURED]** `GeistSans` with `GeistSans Fallback`, root `16px`, but *forms and product chrome run
at 14px*. Weight usage is a three-step rule [REPORTED, consistent with the tokens]: 400 to read, 500
to interact, 600 to announce. Letter-spacing is applied only above ~20 px and tightens as size grows.

#### The move that makes it feel expensive
**The 1 px ring is a `box-shadow`, not a `border`.** Every separated surface in Geist is:

```css
--ds-shadow-border-base: 0 0 0 1px #00000014;
--ds-shadow-border-small: 0 0 0 1px #00000014, 0px 2px 2px #0000000a, 0 0 0 1px hsla(0,0%,98%,1);
--ds-shadow-menu: 0 0 0 1px #00000014, 0px 1px 1px #00000005,
                  0px 4px 8px -4px #0000000a, 0px 16px 24px -8px #0000000f,
                  0 0 0 1px hsla(0,0%,98%,1);
--ds-shadow-modal-elevated: 0px 0px 0px 1px #00000014, 0px 32px 72px -12px #0000000f,
                            0px 8px 32px -12px #00000014, 0px 8px 24px -12px #0000001f;
```

Two consequences. (1) The ring does not consume layout, so a 36 px row is 36 px, hovering does not
shift anything by 1 px. (2) Every shadow is an **alpha black at 3–12%** with a large negative spread,
plus a *second opaque ring in the background colour* (`0 0 0 1px hsla(0,0%,98%,1)`) that seals the
edge against whatever is behind it. That double ring — translucent black outside, opaque paper inside
— is the single detail that makes Vercel menus look like physical objects.

Second move: the focus ring is a **gap ring**.

```css
--ds-focus-ring: 0 0 0 2px hsla(0,0%,100%,1), 0 0 0 4px hsla(212,100%,48%,1);
```

2 px of white, *then* 2 px of blue. The white gap is what makes a focus ring read as deliberate
rather than as a border that got thick.

Third: motion has an overshoot curve and a scale, not a fade.

```css
--ds-motion-overlay-duration: .3s;
--ds-motion-overlay-scale: .96;
--ds-motion-overlay-timing: cubic-bezier(.175, .885, .32, 1.1);
--ds-motion-popover-duration: .2s;
```

The `1.1` final control point overshoots past 1 — a tiny springiness on open. Popovers get 200 ms,
modals 300 ms, both from 0.96 scale.

#### Empty, loading, error
[REPORTED / INFERENCE] The token set carries `red-*`, `amber-*` scales with the full 100–1000 ramp,
implying a `border: red-400 / background: red-100 / text: red-900` callout convention — the same
triplet logic as Temporal. I did not verify live error screens.

### 2.3 Linear

Source: **[MEASURED]** 81 stylesheets fetched and parsed from `linear.app`.

#### Layout skeleton
**[MEASURED]** `--sidebar-width: 232px`. Header heights in the product frame are `57px` / `64px` /
`65px` / `72px` depending on context. The app frame in their own product shots is
`--width: 1320px; --height: 720px; --app-radius: 12px; --frame-padding: 8px` — worth knowing for
your own demo screenshots.

Detail views in Linear are a **split pane**: list on the left, issue on the right, with the URL
updating. That suits issue triage, where you move through many items quickly. **[INFERENCE for AEGIS]**
Your run list → run detail is *not* that: a run detail has 7 pipeline stages, evidence, and a signed
audit block. Take Temporal's route, not Linear's split pane. Take Linear's *sidebar* instead.

#### Density and rhythm
**[MEASURED]** The type scale, with the letter-spacing values, which are the interesting part:

| Style | size | line-height | letter-spacing |
|---|---|---|---|
| tiny | `.625rem` (10 px) | 1.5 | `-.015em` |
| micro | `.75rem` (12 px) | 1.4 | `0` |
| mini | `.8125rem` (13 px) | 1.5 | `-.01em` |
| small | `.875rem` (14 px) | `calc(21 / 14)` = 1.5 | `-.013em` |
| regular | `.9375rem` (15 px) | 1.6 | `-.011em` |
| large | `1.0625rem` (17 px) | 1.6 | `0` |

Note: the product's body size is **15 px**, not 14 or 16. And note `calc(21 / 14)` — they express
line height as an explicit pixel ratio so a 14 px row lands on a 21 px grid.

Buttons: four sizes, and every dimension moves together **[MEASURED]**.

```
24px tall / 12px font / padding 0 10px / gap 4px / icon 12px
32px tall / 13px font / padding 0 12px / gap 8px / icon 16px
40px tall / 15px font / padding 0 14px / icon 18px
44px tall / 16px font / padding 0 20px / gap 6px
```

Radius scale: `4 / 6 / 8 / 12 / 16 / 24 / 32 / 50% / 9999px`.

#### Colour discipline
Four background levels, exactly **[MEASURED]**:

```
light: --color-bg-level-0:#fff  level-1:#f8f8f8  level-2:#f4f4f4  level-3:#f0f0f0
dark:  --color-bg-level-0:#08090a level-1:#0f1011 level-2:#141516 level-3:#191a1b
```

And then the thing almost nobody copies: **`line` tokens and `border` tokens are different families.**

```
/* hairlines / dividers / table rules — light theme */
--color-line-tint:#f4f4f5  --color-line-quaternary:#f4f4f4  --color-line-tertiary:#f0f0f0
--color-line-secondary:#eaeaeb  --color-line-primary:#d4d4d6

/* control borders — inputs, buttons, cards */
--color-border-primary:#e9e8ea  --color-border-secondary:#e4e2e4  --color-border-tertiary:#dcdbdd
--color-border-translucent:#0000000d  --color-border-translucent-strong:#00000014
```

Dividers are *lighter* than control borders. A table rule at `#f0f0f0` and an input border at
`#e4e2e4` are doing different jobs and must not share a token. **This is AEGIS's biggest single
structural gap** — you have one `--border: #dcdad6` and a `--grid: #eceae6`, which is the right
instinct but is only two steps and `--grid` is not wired through the component layer.

Text is never pure black **[MEASURED]**: `#282a30 / #3c4149 / #6f6e77 / #62666d` light;
`#f7f8f8 / #d0d6e0 / #8a8f98 / #62666d` dark.

One accent (`--color-accent: #7170ff`, brand `#5e6ad2`), plus a *semantic* hue set used sparingly:
`blue #4ea7fc`, `orange #fc7840`, `red #eb5757`, `green #27a644`, `yellow #f0bf00`, `teal #00b8cc`.

`--border-hairline` is **`.5px`** on hi-DPI and `1px` otherwise — they actually ship a sub-pixel rule.

#### Typography
**[MEASURED]** `"Inter Variable"` for sans, `"Berkeley Mono"` for mono. The weight ramp is the
signature:

```
--font-weight-light: 300
--font-weight-normal: 400
--font-weight-medium: 510
--font-weight-semibold: 590
--font-weight-bold: 680
```

**510, 590, 680** — non-integer stops only available on a variable font. 510 is *just barely* heavier
than 400; it lifts a label without making it shout. Geist Sans is variable, so AEGIS can do this
today.

#### The move that makes it feel expensive
**Asymmetric hover timing, encoded as tokens** **[MEASURED]**:

```css
--speed-highlightFadeIn: 0s;
--speed-highlightFadeOut: .15s;
--speed-quickTransition: .1s;
--speed-regularTransition: .25s;
```

A row highlight appears in **zero milliseconds** and fades out over **150 ms**. This is why Linear
feels instant while still feeling smooth: the response to your input is immediate, and only the
*decay* is animated. Everyone else transitions both directions at 150–200 ms and the product feels
laggy on hover. This is a two-line change in AEGIS and it is the highest-ROI item in this document.

Second move: `--shadow-stack-low`, a six-layer shadow with an **inset top highlight** **[MEASURED]**:

```css
--shadow-stack-low:
  0px -1px 1px 0px #0000001c inset,
  0px 8px 2px 0px #0000,
  0px 5px 2px 0px #00000003,
  0px 3px 2px 0px #0000000a,
  0px 1px 1px 0px #00000012,
  0px 0px 1px 0px #00000014;
```

Five external layers at 0%→8% alpha with *increasing* blur, plus a 1 px inset shadow from below.
Compare their flat shadows: `--shadow-low: 0px 1px 4px -1px #00000017`,
`--shadow-medium: 0px 3px 12px #00000017`, `--shadow-high: 0px 7px 24px #0000000f` — note that the
*higher* the elevation, the *lower* the alpha. Big soft shadows must be fainter, not darker.

#### Empty, loading, error
[REPORTED, widely documented] Linear's approach is that there is no loading state for anything the
client already knows — the local store answers, so lists render instantly and reconcile in the
background. **[INFERENCE for AEGIS]** You cannot copy the sync engine, but you can copy the *rule*:
never show a spinner for data you could have optimistically rendered from the list you just came
from. Render the run's known fields from the list row, and fill in the stages as they arrive.

### 2.4 Sentry

Source: **[SOURCE]** `getsentry/sentry@master` —
`static/app/utils/theme/theme.tsx`, `.../scraps/tokens/size.tsx`, `.../scraps/tokens/typography.tsx`.
Both token files carry `// AUTOGENERATED BY @DESIGN-ENGINEERING / DO NOT EDIT THIS FILE MANUALLY`.

#### Layout skeleton
**[SOURCE]** `z-index: { sidebar: 1020, sidebarPanel: 1019 }` — the sidebar sits *above* its own
flyout panel, so the panel slides out from behind the rail. Breakpoints:
`0 / 500 / 800 / 992 / 1200 / 1440 / 2560`. Container widths
`320 / 384 / 448 / 512 / 576 / 640 / 768 / 896 / 1024 / 1152 / 1280`.

#### Density and rhythm
**[SOURCE]** Spacing: `0, 2, 4, 6, 8, 12, 16, 24, 32`. The **6 px** step is the unusual one — most
4 px scales skip it, and it is exactly what you want for tight control padding where 4 is cramped and
8 is loose.

Border widths: `0 / 1 / 1.5 / 2 / 4`. (A `1.5px` border token — used for emphasis without going to a
full 2 px, which always looks clumsy.)

Radius: `0 / 3 / 4 / 5 / 6 / 8 / 12 / 16 / 999`. The 3 and 5 exist for nested radii.

Elevation as a *distance*, not a shadow string: `sm: 1px, md: 2px, lg: 4px, xl: 6px`.

Buttons **[SOURCE]**: `36px / 32px / 28px` heights, with `fontSize 0.875rem / 0.875rem / 0.75rem`
and a fixed `lineHeight: '1rem'`, mapped to `radius.lg / radius.md / radius.sm`. Note the fixed
16 px line-height across all three — that is what keeps icon and label baselines aligned.

#### Colour discipline
[SOURCE, partial — the colour token file is large and structured as semantic `tokens.background.*`,
`tokens.content.*`, `tokens.interactive.link.accent.rest`, plus a `tokens.syntax.*` family for code.]
The relevant architecture point: Sentry has a **dedicated syntax-highlighting token family inside the
theme**, so code blocks are themed by the same system as the UI rather than by a third-party
highlighter's palette. For AEGIS, evidence excerpts and policy DSL snippets should follow this rule.

#### Typography
**[SOURCE]**

```
family.sans: "Rubik, 'Avenir Next', sans-serif"
family.mono: "'Roboto Mono', Monaco, Consolas, 'Courier New', monospace"

size: xs 11px, sm 12px, md 14px, lg 16px, xl 20px, 2xl 24px, 3xl 32px, 4xl 40px

weight.sans: { regular: 400, medium: 500 }
weight.mono: { regular: 425, medium: 500 }

lineHeight: { compressed: 1, default: 1.2, comfortable: 1.4, fixed: '1rem' }
```

**Mono regular is 425.** Monospace faces at the same nominal weight read lighter than their sans
counterpart because the glyphs are wider with the same stem width; Sentry compensates with +25 units
of variable weight. If you set a run ID in Geist Mono 400 next to a label in Geist Sans 400, the ID
looks washed out. Bump the mono to 425.

An 11 px `xs` step is also notable — it exists specifically for table meta and timestamps.

#### The move that makes it feel expensive
**Four named easing curves with separate enter and exit** **[SOURCE]**:

```js
motionDurations = { fast: 120, moderate: 160, slow: 240 }   // ms

motionCurves = {
  smooth: [0.72, 0, 0.16, 1],
  snap:   [0.8, -0.4, 0.5, 1],
  enter:  [0.24, 1, 0.32, 1],
  exit:   [0.64, 0, 0.8, 0],
}
```

Read them: `enter` is `cubic-bezier(0.24, 1, 0.32, 1)` — a near-vertical launch that decelerates hard,
so things arrive fast and settle. `exit` is `cubic-bezier(0.64, 0, 0.8, 0)` — accelerating away, no
deceleration, so things leave without lingering. `snap` has a **negative** first control point
(`-0.4`), which means it *anticipates* — pulls back slightly before moving. `smooth` is a strong
ease-in-out for layout shifts.

Combined with Linear's asymmetry insight, the rule is: **enter fast and decelerate; exit accelerating
and shorter**. 120 ms exit / 160 ms enter is a good default pair for AEGIS.

Second: they disable all motion in tests via `IS_ACCEPTANCE_TEST` and an `EMPTY_TRANSITION`. Ship the
same escape hatch, plus `prefers-reduced-motion` — in a plant control room that is not a nicety.

#### Empty, loading, error
Sentry's whole product is the error state, and the pattern it has converged on is: **the error is the
content, and the page around it stays completely normal.** No red page chrome, no alarm styling. The
issue row is a normal row; the *level* is a small coloured token at the start of it. That is the
right model for AEGIS: a failed verification should not turn the run detail page red. It should be a
run detail page whose verification stage carries a `critical` token and an expanded reason block.

#### Colour discipline

Status **[SOURCE]**, note every status has a `main` (fill) and a `text` (on-paper) variant:

| | dark main | dark text | light main | light text |

| success | `#1a7f4b` | `#6ccf8e` | `#1b855e` | `#0a764e` |

consistency. AEGIS's `--approval: #d97706` is a single value doing both jobs; it will fail as text
on a `#d97706` fill.

One more: `action.selectedBorder` is **orange** (`#ff9900`), not the primary blue — the selection

reads as "this is a link".

**[SOURCE]** `'Inter', 'Helvetica', 'Arial', sans-serif` and `'Roboto Mono', monospace`. Weights
`light 300 / regular 400 / medium 500 / bold 500` — **bold is also 500**. Grafana refuses to go above
medium anywhere in the UI. Restraint enforced at the token layer.

#### The move that makes it feel expensive
Honestly: Grafana does not feel expensive, and the reason is instructive. **[MEASURED]** its
transitions are `0.25s cubic-bezier(0.4, 0, 0.2, 1)` — Material's standard curve, at 250 ms, on
`background-color, border-color, color`. That is 2.5× Linear's 100 ms default and it makes the UI
feel slightly syrupy on hover. **The lesson is the counter-example: 250 ms on hover is the single
most common thing that makes a competent console feel cheap.** Check AEGIS for `transition: all 0.2s`
and kill it.

What Grafana *does* get right and is worth taking: the whole product is legible at 14/22 from three
feet away, forever, with no eye strain, because of the even-multiples rule and positive tracking.

#### Empty, loading, error
[MEASURED, partial] Panels show errors *in place*, inside the panel frame, with the panel header and
its title intact — you never lose your place in the dashboard because one query failed. The panel's
corner gets an error affordance rather than the panel being replaced. **This is the pattern for AEGIS
stage cards:** a failed stage keeps its position, its label and its timestamp; only its body swaps to
the failure reason.

### 2.6 Stripe Dashboard

### 2.7 Supabase Studio

Source: **[MEASURED]** live CSS from `supabase.com/docs`, which ships the Supabase UI token layer.

#### Layout skeleton
**[MEASURED]** The token names tell the shell: `--background-dash-canvas`, `--background-dash-sidebar`
— and they are **both set to `var(--background)`**. The sidebar and the canvas are the *same colour*.
Separation is done entirely by a hairline. A four-step surface ladder sits on top:
`--background-surface-75 / -100 / -200 / -300 / -400`.

#### Density and rhythm
**[MEASURED]** `--border-radius: 8px` with a ramp `xs 2 / sm 4 / lg 8 / xl 16`, and a
`--borderradius-tableheader: 4px` — a dedicated radius token just for table headers. Border widths
`xs 1 / sm 2 / md 4 / lg 8`.

#### Colour discipline
This is the section to actually act on. **[MEASURED]** Supabase does not have a border *palette*. It
has a border *formula*:

```css
--border: oklch(from var(--foreground)
                l
                calc(c * .54)
                h / calc(2% + 20% * var(--contrast-border)));

--border-stronger: oklch(from var(--foreground)
                l calc(c * .5) h / calc(5% + 45% * var(--contrast-border)));

--border-control-hover: oklch(from var(--foreground)
                l calc(c * .5) h / calc(12% + 58% * var(--contrast-border)));

--border-overlay: oklch(from var(--foreground)
                l calc(c * .5) h / calc(4% + 34% * var(--contrast-border)));
```

Read it: every hairline is the **foreground colour, at roughly half its chroma, at a low alpha**.
The hue is inherited from the ink, so on a warm page the rules are warm; on a cool page they are cool.
They never go grey and never go dirty. And `--contrast-border` is a **user-facing 0→1 knob** that
scales every border's alpha simultaneously — an accessibility control that costs one variable.

Backgrounds are generated the same way:

```css
--background: oklch(var(--surface) calc(var(--chroma) * .5) var(--surface-hue));
```

Measured live body background: `oklch(0.995 0 34)` — a near-white at **hue 34°**, i.e. warm. Supabase
already ships a warm paper.

Status borders are a single consistent rule **[MEASURED]**:

```css
--border-brand:       oklch(from var(--primary)     l c h / 30%);
--border-destructive: oklch(from var(--destructive) l c h / 30%);
--border-info:        oklch(from var(--info)        l c h / 30%);
--border-warning:     oklch(from var(--warning)     l c h / 30%);
```

**Every status border is exactly 30% alpha of its status colour.** One rule, four applications, zero
hand-picked hex values. For AEGIS's four-colour palette this is a direct drop-in: you get eight new
correct tokens (4 borders + 4 surfaces) from your existing four, with no new decisions.

#### Typography
**[MEASURED]** Inter with a long fallback chain; docs body `16px`. Studio proper runs denser
**[INFERENCE]**.

#### The move that makes it feel expensive
The OKLCH relative-colour syntax (`oklch(from var(--x) l c h / 30%)`). It is supported in every
browser you care about in 2026, it works fine under Tailwind v4, and it means your status system has
**one** source of truth per status instead of three near-values that drift. When someone tweaks
`--critical`, the critical border and critical surface move with it, correctly, forever.

#### Empty, loading, error
Not observed directly. The presence of `--border-info` / `--border-warning` /
`--border-destructive` as first-class tokens implies a standard inline-callout component
**[INFERENCE]**.

## 3. Patterns worth stealing — 22 one-line instructions

Each is written so an engineer can act on it today. Source product named.

**Colour & surface**

1. Split `--border` into two families: `--line-*` for dividers and table rules (lighter) and
   `--border-*` for control borders (darker). Ship at least 3 steps each. *(Linear)*
2. Derive every hairline from the foreground colour in OKLCH at ~half chroma and low alpha —
   `oklch(from var(--foreground) l calc(c * .54) h / 12%)` — so rules inherit the paper's warmth
   instead of reading grey. *(Supabase)*
3. Add a `--contrast-border` multiplier (0→1) that scales every border alpha at once, and expose it
   in settings as a high-contrast toggle. *(Supabase)*
4. Generate all four status *surfaces* and *borders* from the four status colours with
   `oklch(from var(--critical) l c h / 30%)` for borders and `/ 8%` for fills — never hand-pick them.
   *(Supabase)*
5. Ship **two** values per status: one for text on paper, one for text on that status's own fill.
   Grafana's warning is `#ff9900` as a fill and `#b04e0c` as light-theme text. *(Grafana, Temporal)*
6. Make the selected-row indicator a different hue from the interactive accent, so "selected" never
   reads as "link". *(Grafana — `action.selectedBorder` is orange while primary is blue)*
7. Stop using pure black ink. Move `--foreground` to a warm-shifted deep neutral; Stripe ships
   `#3c4257` on white. *(Stripe)*
8. Keep exactly four background levels and never add a fifth — canvas, surface, sunken, raised.
   *(Linear's `bg-level-0..3`)*
9. Use solid greys for fills and **alpha** greys for anything overlaying something else, as two
   separate token families. *(Vercel — `--ds-gray-*` vs `--ds-gray-alpha-*`)*
10. Scrim modals with a *light* warm near-white at 0.8 opacity, not black — on paper-coloured UI a
    black scrim looks cheap. *(Vercel — `--ds-overlay-backdrop-color: hsla(0,0%,95%,1)`)*

**Elevation & separation**

11. Make every card/menu/panel edge a `box-shadow: 0 0 0 1px <alpha-black>` ring rather than a
    `border`, so hover and focus never shift layout by 1 px. *(Vercel)*
12. Seal every floating surface with a **double ring** — translucent black outside, opaque
    background-colour inside: `0 0 0 1px #00000014, …, 0 0 0 1px <bg>`. *(Vercel `--ds-shadow-menu`)*
13. As elevation rises, make the shadow *fainter and softer*, not darker: `1px/4px @ 9%` →
    `3px/12px @ 9%` → `7px/24px @ 6%`. *(Linear `--shadow-low/medium/high`)*
14. Put a `0 -1px 1px inset rgba(0,0,0,.11)` under raised rows/cards for a hairline bottom seat.
    *(Linear `--shadow-stack-low`)*
15. Delete card chrome from the run detail: render the 7 pipeline stages as rows in one container
    separated by `--line-*` hairlines, not as 7 `<Card>`s. *(Stripe's card-less dashboard)*

**Motion**

16. Set hover-in to `0s` and hover-out to `150ms`. Highlight appears instantly, decays gently.
    *(Linear — `--speed-highlightFadeIn: 0s; --speed-highlightFadeOut: .15s`)*
17. Use separate enter and exit easings: enter `cubic-bezier(0.24, 1, 0.32, 1)` at 160 ms, exit
    `cubic-bezier(0.64, 0, 0.8, 0)` at 120 ms. *(Sentry)*
18. Open overlays from `scale(0.96)` over 200 ms (popover) / 300 ms (modal) with
    `cubic-bezier(.175, .885, .32, 1.1)` — the `1.1` endpoint gives a barely-perceptible overshoot.
    *(Vercel)*
19. Audit for `transition: all 0.2s` / `0.25s` and replace with a 100 ms default on
    `background-color, border-color, color` only. *(Linear's 0.1s vs Grafana's 0.25s — the
    difference is visible)*

**Type & density**

20. Set mono at weight **425**, not 400, so run IDs and hashes optically match adjacent sans labels.
    Geist Mono is variable, so this works today. *(Sentry)*
21. Use the variable-font weight stops `400 / 510 / 590` instead of `400 / 500 / 600`; 510 lifts a
    label without shouting. *(Linear)*
22. Lock control heights to exactly three — `32 / 36 / 40` — and bind font size and radius to each,
    so no component invents a fourth. *(Vercel `--ds-size-small/medium/large`)*
23. Set table and list rows at **36 px** with 14 px / 22 px text; keep every font size and line
    height an even number so baselines land on a shared grid. *(Grafana — enforced with a `throw`)*
24. Give popovers/menus a 6 px pad, 36 px rows, 8 px row padding and a row radius one step below the
    container's, so radii nest concentrically. *(Vercel `--ds-popover-*`)*
25. Order your z-index so **menus sit above modals** (`drawer 200 < modal 300 < menu 2001 <
    toast 5000 < tooltip 99999`) — a select inside a modal must not clip. *(Vercel)*
26. Make the focus ring a **gap ring**: 2 px in the background colour, then 2 px in the accent.
    *(Vercel `--ds-focus-ring`)*

**Information architecture**

27. Open run detail as a **route**, not a drawer or a split pane — an auditor must be able to send a
    URL that lands on a specific evidence item. *(Temporal)*
28. Give *pipeline stage taxonomy* its own hue budget, used only as thin rails and glyphs, entirely
    separate from the four status colours which own fills and text.
    *(Temporal `action.workflow.*` — 6 taxonomy hues alongside 4 status hues)*
29. Name sidebar items after the job, not the data model: `Review queue`, not `Verification`.
    *(Stripe)*
30. Keep two distinct reds: one for *destructive user action* and one for *the system failed*. They
    must not be the same token. *(Temporal — `danger` vs `error`/persimmon)*
31. Render disabled state as `opacity: 0.32` on the live colour, not as a grey substitute, so
    disabled items keep their hue. *(Temporal `opacity.disabled`)*

**Failure honesty**

32. When a stage fails, keep the stage row in place with its label, index and timestamp intact, and
    swap only its body for the failure reason. Never turn the page red. *(Grafana panel errors,
    Sentry issue rows)*
33. Theme code/evidence excerpts from your own design tokens, not from a highlighter's default
    palette — ship a `syntax.*` token family. *(Sentry)*
34. Never spin for data you already hold: render the run's known fields straight from the list row
    you navigated from, then fill in stages as they resolve. *(Linear)*

## 4. Anti-patterns — what these products do that would be WRONG for AEGIS

These are all good decisions *for them* and bad decisions *for an air-gapped, evidence-bearing
compliance console*. Listed with the reason.

1. **Optimistic UI / local-first writes (Linear).** Linear's whole feel depends on the client
   asserting a mutation before the server confirms it. In AEGIS, a human approval is a legally
   meaningful act that must be signed server-side before it is shown as done. You may optimistically
   render *reads*; you must never optimistically render *an approval, a signature, or a verification
   result*. Show the pending state honestly.

2. **Skeleton screens that fake structure (most of the list).** A skeleton implies "content of this
   shape is arriving". If the evidence retrieval might return *nothing*, or might fail, a skeleton is
   a lie told at 60 fps. Use an explicit "retrieving evidence…" state with a real progress signal, or
   nothing at all.

3. **"Something went wrong" / friendly error copy (Vercel, Supabase, most SaaS).** Consumer products
   soften errors to reduce churn. A plant inspector needs the error code, the stage, the timestamp
   and the upstream cause. Every failure surface in AEGIS should carry a copyable identifier.

4. **Illustrated, cheerful empty states (Supabase, Railway, Resend).** Mascots and gradients in an
   empty queue undercut the product's claim to be an instrument of record. Empty states here should
   be a single line of plain text plus, where applicable, the reason the set is empty ("No runs match
   this filter" ≠ "No runs exist" ≠ "You lack read permission on this namespace" — three different
   empty states, three different messages).

5. **Telemetry-shaped design decisions.** Several of these products' patterns (onboarding checklists,
   "what's new" popovers, nudge toasts, product-tour spotlights) assume an internet-connected
   analytics loop. AEGIS is air-gapped; anything that phones home is not just unnecessary, it is a
   compliance liability. Do not build UI that implies it.

6. **Gradients and brand glow (Grafana's `brandHorizontal`, Linear's marketing surfaces, Vercel's
   `--geist-text-gradient`).** A gradient in a compliance console reads as marketing. Keep the
   product surface strictly flat; if you want warmth, get it from the paper tint, not from a fill.

7. **Dark mode as the default (Linear, Raycast, Vercel, Grafana).** Dev tools default dark because
   developers work at night. Industrial inspection reports get printed, projected and read under
   plant lighting. Keep the warm-paper light theme as the default and canonical theme; ship dark as
   the alternate. Your existing `--ink-*` token family is the right structure for this.

8. **Density toggles as a user preference (reported for table UIs generally).** Tempting, but a
   compliance console's screenshots end up in evidence packs. If two auditors see different row
   heights, screenshot comparison gets harder. Pick one density, tune it properly, and ship it.

9. **Colour as the sole status carrier (everywhere).** Every one of these products leans on colour
   alone in at least one place. For AEGIS, each of the four statuses needs a distinct **glyph** and
   a **text label** as well as a colour — both for colour-vision deficiency and because a black-and-
   white printout of a run report must still be unambiguous. Print is a real output here.

10. **Command palette as the primary navigation (Raycast, Linear, Warp).** Beautiful, and worth
    having — but a hidden primary path fails an operator who has been trained on a written SOP, and
    it fails a judge clicking through in 90 seconds. Ship ⌘K as an accelerator over a navigation that
    is fully visible and fully clickable.

11. **Infinite scroll on lists (several).** Audit work needs stable pagination with page numbers and
    total counts, because "row 412 of 1,908" is a citable position and "somewhere down the infinite
    list" is not.

12. **Relative timestamps only ("3m ago") (Linear, Sentry, Vercel).** Fine for triage, wrong for
    evidence. Show absolute UTC with an explicit offset as the primary value and relative time as the
    secondary/hover. A run's audit record has no "ago".

13. **Auto-refresh that silently reorders rows (Grafana, Datadog).** In a live queue this rips the
    row out from under a cursor mid-approval. If you poll, buffer the change and surface a
    "3 new runs — refresh" affordance instead of mutating the list in place.
